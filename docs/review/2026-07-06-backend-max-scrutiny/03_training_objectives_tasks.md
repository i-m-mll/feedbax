## Architecture Assessment

Two training pipelines coexist at sharply different maturity levels. The native/executor path (`executor.py`, `checkpoint_custody.py`, `worker_validation.py`) is well-built — atomic temp-dir-then-rename writes, content-addressed manifests, and generic restoration of every declared state slot including optimizer state — resolving b1860d5 and ae2d692 for that path. The legacy `TaskTrainer` in `trainer.py` retains the exact optimizer-state-discard bug those issues were opened for, plus an independently-discovered, more acute bug: on resume, the RNG key array is indexed by a global batch counter that outruns its own length, either crashing or silently clamping to reuse the last key for the remainder of training. `_train_step` itself is clean and confirms d8f6b09 and 52774c3 hold. This same "old simple path lags the new contract-driven path" pattern recurs three more times independently across the reviewed slices: `train_ppo` was never brought up to the `lax.fori_loop`/single-jit standard applied to `train_ppo_batched`; the legacy `LossTermSpec` reduction stack in `service.py` disagrees with the modern `ObjectiveSpec` stack on what `"l2"` even means and forecloses trial-grouped reduction (directly touching 63230c3); and `task.py`'s intervention-parameter evaluation duplicates `intervene/schedule.py`'s version with different (and in one case entirely absent) RNG key-splitting. None of these are hypothetical — each is evidenced by reading the divergent implementations side by side.

The objectives layer's core (`AbstractLoss`/`CompositeLoss`/`TermTree` in loss.py) is genuinely well-designed: composable via operators, correctly immutable, no deprecated `jax.tree_*` calls. The risk concentrates entirely in `service.py`/`spec.py`, which is effectively a second loss-authoring system bolted alongside the original hierarchy, with a dedicated legacy reduction/metric pipeline that has already produced one clear correctness bug (`"l2"` = `abs`, not Euclidean) and one open architectural gap (63230c3 not fully closed). Schema discipline is good where deliberately built (`ObjectiveSpec`'s `OBJECTIVE_SCHEMA_VERSION` + migration function) but doesn't extend to `LossTermSpec` ingestion, and `value_dtype` metadata is captured but functionally inert — a d8f6b09-adjacent gap that was never actually touched by that work, not a partial fix.

`intervene/` is small and mostly sound: `lax.cond`-gated activation avoids Python branching on traced values, so there's no recompilation risk from intervention toggling. Its weaknesses are duplication (three near-identical force-channel components), one real RNG correlation bug (`AddNoise` reusing one key across PyTree leaves), an orphaned scheduling helper left with dead commented-out code beside it, and a composability model that relies entirely on implicit graph-wiring order with no port-collision validation. `task.py` is the highest-risk single file reviewed: at 2188 lines it is an unambiguous god-module spanning trial-spec data types, dtype plumbing, intervention-parameter evaluation (duplicated and RNG-divergent from `intervene/schedule.py`), the full ensemble-eval API, three task geometries, and a graph-adapter component — six responsibilities that would each support an independently reviewable file, with the file's own docstring already admitting parts of the mess. Validation strictness for intervenor labels also differs between `prepare_trial` (raises) and the actual in-graph training path `TaskComponent.__call__` (does not) — the less-strict path being the one that runs in production is a real gap given CLAUDE.md's "graph is the model" emphasis on explicit errors over silent pass-through.

Across all four areas, the single most useful structural intervention would be finishing what's already half-done: retiring (not just deprecating) the legacy `TaskTrainer` path, the standalone `train_ppo`, and the legacy `LossTermSpec` reduction stack, all three of which are older siblings of a more complete, more correct implementation that already exists in the same codebase. CLAUDE.md is explicit that backward compatibility is not a concern here (single developer, no external consumers) — these three legacy surfaces are exactly the kind of retained-but-inferior code path the project's own stated policy would delete outright rather than patch in place. RNG-discipline bugs were the most frequent single class of finding (five separate, independently-verified instances: resume-key indexing, HOLD/REACH key reuse, validation-key waste, AddNoise cross-leaf reuse, and the schedule.py param-eval no-split) — worth a dedicated audit/lint pass (e.g., a static check for `jr.split` results that are computed but never all consumed, and for `jt.map(lambda x: f(key, x), tree)` patterns that should use `jtree.random_split_like_tree`) rather than one-off fixes, since the pattern recurs across unrelated modules.
