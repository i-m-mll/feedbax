## Architecture assessment

The four scoped areas sit at visibly different maturity levels within one codebase, and the gradient tracks recency: newer, more central contract surfaces are the most disciplined, and older or peripheral surfaces lag. `feedbax/contracts/migrations.py` is the standout — a genuine BFS-pathed migration registry over `SchemaMigration` edges, ~80 registered `SpecSchemaFamily` rows with explicit migrate-vs-reject policy, pure dict-in/dict-out migration functions backed by real test files (`tests/test_graphspec_schema_migrations.py`, `tests/test_structured_spec_migrations.py`). This is unusually good architecture for a single-developer research codebase and should be treated as the house style. Its one serious gap — a payload with no `schema_version` field at all is silently treated as current rather than rejected (`migrations.py:450-464`) — undercuts the otherwise-strong reject-unknown-versions posture and should be closed first, since it is the exact failure mode the policy exists to prevent.

The weak spots inside `contracts/` cluster at strictness rather than structure: `GraphSpec`/`ComponentSpec`/`WireSpec` (the literal "graph is the model" payload) and all of `studio_api.py` lack the `extra="forbid"` + schema-identity fields that `manifest.py`'s `StrictModel` pattern already enforces elsewhere in the same package. This means the single most load-bearing spec type in the system is *less* strict than the manifests that wrap it — an inversion of what the "the graph is the model" principle would suggest. The fix is mechanical (add `model_config`, add version fields, add migration-test coverage) rather than a redesign.

`persistence/database.py` and `component_registry/builtins.py` read as pre-contracts-era code that was never brought up to the newer bar. The database layer mixes a full SQLAlchemy ORM stack with a fully separate raw-`sqlite3` manifest index (`manifest_index.py`) with no shared transaction boundary or cross-referencing — concrete evidence for the premise of tracked issue `e33f487`. It also has a decorative `hash_version` column that is written but never read or branched on, an N+1 filesystem-stat storm plus an unconditional silent commit on every session open, no indices on the columns actually filtered in hot query paths, and at least two delete-then-add sequences that can partially commit on crash. None of these are exotic bugs — they are the standard list of "SQLAlchemy code written before anyone thought about it as a service layer" symptoms, and `component_registry/registry.py`'s own versioned-migration machinery (which is done well) shows the team already knows how to do this properly elsewhere in the same directory tree.

The most serious individual finding is `component_registry/cde_templates.py`'s self-documented "display-only" node types (`Input`, `Subtract`, `Reshape`, `MatMul`, `Scale`, `Sigmoid`) that are stored in template graphs but never registered as buildable primitives — a verbatim, in-code-acknowledged instance of the exact anti-pattern CLAUDE.md's Core Principle exists to prohibit ("display-only nodes that shadow real architectural choices... are bugs regardless of how they are labelled"). Nothing in the resolution path currently gates or warns on `template_kind='display'` at graph-build time, so the failure mode is live, not hypothetical, for any user who drags one of these CDE templates onto the canvas. This should be treated as the top-priority fix from this review, ahead of the schema-strictness gaps, because it is a correctness bug against the repo's own foundational rule, not merely a hardening gap.

`config/tree.py` and `config/utils.py` show the same "mostly excellent, one bad regression" shape as `contracts/`: `namespace.py`'s `update_none_leaves` correctly raises when an `None`-sentinel can't be filled, but `tree.py:939-945`'s `_expand_missing_levels` silently synthesizes a placeholder `"_"` key with only a `logger.warning` when an LDict level can't be resolved from a reference tree — the config-tree analog of exactly the graph-construction anti-pattern the repo's core principle targets, just one layer removed from the graph engine itself. Combined with `tree.py`'s near-total absence of dedicated unit tests despite 1003 lines of intricate PyTree-structural logic, this is a real risk pocket that a determined reviewer would want closed before trusting derived hyperparameter trees for anything schema-sensitive.

Taken together, this is not a codebase in architectural trouble. It is a codebase where a strong, thoughtful contracts/migration discipline has been established recently and has not yet been backported to the surfaces (database.py, builtins.py, the graph spec models themselves, tree.py's edge cases) that predate it. The fix pattern is consistent across nearly every finding: apply the `extra="forbid"` + schema-identity + versioned-migration template already proven out in `migrations.py` and `component_registry/registry.py` to the remaining surfaces, and replace the handful of silent-default/silent-accept fallbacks with the loud, clear errors the repo's own CLAUDE.md already mandates.
