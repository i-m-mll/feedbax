### `feedbax/analysis/`

**AN-1** — `md5_str` cache/graph-identity key omits dependency wiring | **high** | analysis.py | `feedbax/analysis/analysis.py:2526-2527`: `#! TODO: add leaves from self.inputs and make sure any referenced AbstractAnalysis instances are resolved to their own md5_str.` — `md5_str` hashes class name, ops params, and field params but never `self.inputs`. This value is the dependency-graph **node-dedup key** in `_dependencies.py` (`node_id = dep_source.md5_str`), the result-cache filename, and the figure-dump filename. Two `AbstractAnalysis` instances differing only in which upstream dependency they're wired to collide on `md5_str`, which can make `_dependencies.py` silently merge two semantically different graph nodes and reuse one's computed result for the other — the exact "fallback paths that substitute stale values silently" bug class the repo's own CLAUDE.md calls out. A hardcoded placeholder field (`IdentityNode.tmp_label: str = "foo"`, `analysis.py:3040`, comment `#! Remove after we hash inputs`) exists purely to perturb the hash until this is fixed — i.e. the bug is self-acknowledged and shipped anyway. **Proposal**: fold `self.inputs` leaf identities into `md5_str`, recursively resolving nested `AbstractAnalysis` refs to their own `md5_str`; delete the `tmp_label` shim. **Effort**: M. **Overlap**: adjacent to tracked c8c77f2/f22dbf4 (analysis run context / DAG subgraphs) but not itself covered by either title.

**AN-2** — `build_dependency_graph` triple-passes the node set with an uncached property and an O(n) linear scan | **medium** | _dependencies.py | `feedbax/analysis/_dependencies.py:173-236` runs three separate loops (recursive `_add_deps` at 173-203, direct-edge pass 205-220, "transitive edge" pass 222-235), each independently accessing `analysis._flattened_inputs`, which is a bare `@property` (`analysis.py:1109-1133`, not `cached_property`) — every access re-runs `jt.leaves(...)` plus full leaf-type validation. `resolve_dependency_node` (`_dependencies.py:88-142`) additionally does `for k, v in dependency_lookup.items(): if v is dep_source` — a full linear scan — inside a callback invoked from all three passes, giving roughly O(N·D) redundant flattenings and O(N²·D) worst-case scans just to build the graph, before any computation. The third ("transitive") pass also looks logically redundant with `_add_deps`'s recursion, which already walks the full closure. **Proposal**: make `_flattened_inputs` a `cached_property` (the class already uses this pattern for `md5_str`/`_field_params`); replace the linear scan with a reverse `id(instance) -> key` map built once; confirm/remove the apparently-redundant third pass. **Effort**: S-M.

**AN-3** — Cycle detection / topological sort — clean bill of health | n/a | _dependencies.py | `_dependencies.py:244-271` (`topological_sort`) is a correct DFS-based cycle-detecting sort; diamond dependencies are correctly deduplicated in ordering via the `visited` check (line 253). Only latent risk: unbounded Python recursion depth for very deep chains. Noted since dependency-graph correctness was explicitly in scope — no bug found here.

**AN-4** — `_reconstruct_dependencies` re-walks flattened inputs per node, multiplying AN-2's cost | **medium** | _dependencies.py | `_dependencies.py:522-658` (`compute_dependency_results`): actual computation is correctly deduplicated by `md5_str`-keyed `computed_results` (good — the module's stated purpose). But `_reconstruct_dependencies` (line 616) re-walks `_flattened_inputs`/`_input_treedefs` and calls `resolve_dependency_node` again per dependency leaf, per node — compounding AN-2's uncached property across every node in the graph, not just the three graph-building passes. **Proposal**: same root fix as AN-2, plus cache `resolve_dependency_node` results per `(analysis_id, dep_name, dep_source_id)` within one `compute_dependency_results` call. **Effort**: S-M.

**AN-5** — `_collect_ancestors` demand-driven pruning — clean, efficient | n/a | _dependencies.py | `_dependencies.py:489-519` is an iterative stack-based ancestor walk, O(ancestors), no stack-depth risk. Noted as a positive counterexample sitting next to AN-2's less efficient neighbor.

**AN-6** — Staged bundle execution forces `force=True` on every evaluation stage, defeating the eval cache | **high** | bundles.py | `feedbax/analysis/bundles.py:733` (`_execute_evaluation_stage`) calls `execute_evaluation_run_spec(..., force=True)` unconditionally. `execute_evaluation_run_spec` is explicitly designed to skip recompute via `states_path.exists()` by deterministic manifest ID (`evaluation.py:184-208`), and evaluation is called out elsewhere in the codebase as the expensive step (`execution.py:648`). Every bundle re-run — including adding one new analysis stage to an existing bundle — recomputes every evaluation from scratch. **Proposal**: default to `force=False` with an explicit refresh knob for callers that need invalidation. **Effort**: S.

**AN-7** — `execute_analysis_run_spec` has no manifest-reuse check at all, unlike its evaluation-stage sibling | **high** | specs.py / bundles.py | `feedbax/analysis/specs.py:230-291`, invoked from `bundles.py:745` and `:826`. Never computes `analysis_run_manifest_id(spec)` and checks for an existing manifest before calling `recipe(...)` — in contrast to the evaluation path's explicit existence gate. Every analysis/materialization stage recomputes unconditionally. **Proposal**: mirror the evaluation-stage pattern — compute manifest ID up front, skip on hit, gate behind the same force/refresh flag proposed in AN-6. **Effort**: M.

**AN-8** — Legacy pickle cache key for evaluated states omits the PRNG key | **high** | execution.py / persistence/database.py | `feedbax/analysis/execution.py:672-762` (`run_evaluation`) via `generate_eval_hash`/`add_evaluation` in `persistence/database.py:1146-1243`: the legacy (non-manifest) states cache filename is derived from model hashes, eval parameters, experiment name, and setup metadata — but not from the `key` (JAX PRNG key) threaded into `eval_fn(key, hps, model, task)`. Two calls with identical hyperparameters but different `key` collide on the same cache file; the second call silently loads the first's stale, wrong-seed states (`loaded_from_pickle=True` reports success, no diagnostic). **Proposal**: fold a stable digest of the key/seed into the hash inputs. **Effort**: S.

**AN-9** — Bundle manifest lookup does a full filesystem glob+parse instead of using the existing SQLite index | **medium** | bundles.py | `feedbax/analysis/bundles.py:313-325` (`iter_candidate_manifests` → `iter_manifest_files`) globs `manifests_dir.glob("**/*.json")` and loads+validates every manifest ever written, even though `persistence/manifest_index.py` maintains a SQLite index built for exactly this "manifests of kind X" query. Cost grows linearly with total historical manifest count, on every bundle execution. **Proposal**: query the SQLite index first, only `load_manifest` on candidate matches. **Effort**: M.

**AN-10** — `AnalysisBundleSpec` schema validation checks `depends_on_roles` ordering but never validates plain `depends_on` | **medium** | bundles.py | `feedbax/analysis/bundles.py:161-184` (`_validate_schema_and_payload`) iterates `stage.depends_on_roles` against seen stage names but never touches `stage.depends_on` (declared line 109) — a typo'd/forward-referenced entry passes validation and only fails at execution time inside `_resolve_stage_inputs` with a generic "unknown stage" error. **Proposal**: validate `depends_on` symmetrically. **Effort**: S.

**AN-11** — Power-iteration `while_loop` recomputes the same step twice per iteration | **medium** (perf) | grad.py | `feedbax/analysis/grad.py:561-584` (`reducer_opnorm_power_bidiag`): `cond(carry)` computes `one_step(v_prev)` to check convergence delta, then `body(carry)` independently recomputes `one_step(v_prev)` for the same carry to advance state — doubling linear-operator (JVP/VJP through the model) applications per iteration since `cond`'s result isn't threaded into `body`. **Proposal**: restructure so `one_step` is computed once per iteration (thread forward, or use masked `lax.scan` instead of `lax.while_loop`). **Effort**: M.

**AN-12** — Nested Python loop re-derives `jax.grad` from scratch per cell instead of once, and isn't vmapped | **medium** | grad.py | `feedbax/analysis/grad.py:679-687` (`hessian_block_opnorm_matrix_u`): builds a k×k grid of block operator-norms via nested Python loops; each cell's `hessian_block_linop_ij` independently derives `g_sel = jax.grad(phi, argnums=idxs)` from scratch (line 534), re-traced k² times, with none of the k² independent power iterations vmapped despite identical fixed shape. **Proposal**: hoist `g_sel` construction outside the double loop at minimum; consider vmap-over-grid for the power iterations. **Effort**: M.

**AN-13** — Self-flagged silent-truncation bug in gradient unzip path | **critical** | grad.py | `feedbax/analysis/grad.py:41-55` (`_compute_grads`): code carries its own comment `#! Something is wrong here.` directly above `jtree.unzip(grads_raw, tuple_cls=_Tuple)`. `jax_cookbook.tree.unzip` does a plain Python `zip(*tree_flat)` with no arity validation — if any function in a batch produces a differently-shaped or non-`_Tuple` gradient result, columns are silently dropped rather than erroring. **AN-14** — Hutchinson trace/Frobenius-norm reducers default to a fixed shared `PRNGKey(0)` | **medium** | grad.py | `feedbax/analysis/grad.py:595,614` (`reducer_frobenius_hutchinson`, `reducer_trace_hutchinson`): `key=jax.random.PRNGKey(0)` as a literal default, unlike every other PRNGKey default site in `analysis/` (`network.py:107`, `fps.py:80`, `regression.py:250`), which use `field(default_factory=lambda: jr.PRNGKey(0))`. **AN-15** — `_apply_fig_ops` silently proceeds on mismatched/missing dependency structure instead of raising | **medium** | analysis.py | `feedbax/analysis/analysis.py:2919-2939`: when per-dependency figure-panel keys disagree with a reference dependency's keys, or no dependencies/leaves are found, the code logs a warning/error and either proceeds with the (possibly wrong) reference ordering, or silently falls back to calling `make_figs` directly — dropping the requested fig-op transform. ## Architecture assessment

The `analysis/` package is the most structurally overdue piece of this scope. `analysis.py` at 3164 lines is not one god-class so much as five distinct subsystems welded onto a single `AbstractAnalysis` class: (1) the core compute/make_figs dispatch contract; (2) a dependency/input-spec DSL that `_dependencies.py` treats as an external interface (`md5_str`, `_flattened_inputs`, `_input_treedefs`); (3) a large fluent pipeline-builder DSL (`vmap`, `map_compute`, `after_*`, `combine_figs_by_*`) that is self-contained and only loosely coupled to dependency resolution; (4) figure-emission/saving glue (`save_figs`, `save_outputs`, the `_FigOp`/`FigureSaveTask` machinery); and (5) identity/caching (hashing, the dill pickle cache). These seams are clean enough that a four-way split (core contract + input DSL types stay in `analysis.py`; pipeline DSL to `analysis/builders.py`; figure emission to `analysis/figs.py`; identity/caching to `analysis/identity.py` or folded into `_dependencies.py`) would shrink the core file to roughly 1200-1500 lines while making each remaining piece independently testable. The identity/caching seam is the most urgent to extract on its own merits, independent of file size: `md5_str` is simultaneously the dependency-graph dedup key, the result-cache filename, and the figure-dump filename (AN-1), and it has a self-acknowledged correctness gap (it excludes `self.inputs`) that is currently patched with a literal placeholder field whose only job is to perturb a hash. That is a live correctness bug sitting in code the rest of the module treats as foundational — it deserves fixing before any restructuring, not as a side effect of it.

The dependency-resolution layer (`_dependencies.py`) is smaller and, encouragingly, is *correct* where it matters most: topological sort correctly detects cycles and dedupes diamond dependencies in traversal order, and the actual computation cache (`computed_results` in `compute_dependency_results`) correctly avoids recomputing shared upstream nodes. The problems here are performance, not correctness — an uncached `@property` (`_flattened_inputs`) gets re-evaluated on every one of three redundant graph-building passes and again once per node during reconstruction, combined with an O(n) linear scan standing in for what should be a dict lookup. None of this is algorithmically hard to fix (cached_property plus a reverse-id map), and it is worth doing before the pipeline scales to larger bundles, since the redundancy compounds multiplicatively rather than additively.

The execution/caching story across `execution.py` and `bundles.py` is inconsistent in a way that actively costs wall-clock time today: the evaluation-stage path in staged bundles hardcodes `force=True`, unconditionally bypassing a cache that's explicitly built for reuse, while the sibling analysis-stage path has no cache-lookup mechanism at all despite `bundles.py` elsewhere showing awareness of manifest-based identity (it just never wires the analysis path up to it). This is the single highest-leverage runtime fix in the whole `analysis/` scope, because it means every staged-bundle re-run — including the common case of adding one new analysis stage to an otherwise-unchanged bundle — silently pays for a full re-evaluation.

The `plot/` package's central finding is the mirror image of a common "keep DRY" failure: two backends (matplotlib, plotly) implement what look like the same plots, but they have quietly diverged in capability (matplotlib profile plots lack the aggregation the plotly ones have) and in parameter honoring (one backend silently ignores a parameter the other implements), while duplicating substantial boilerplate (colormap sampling reimplemented roughly eleven times despite an existing shared helper). None of this is exotic to fix — the data-prep/color logic is naturally backend-agnostic — but the fact that a user switching backends for what they believe is the same figure gets different analytical content is a real correctness-adjacent trap, not just a maintenance annoyance. Separately, the `io.py` save_figure contract that rlrmp explicitly depends on is more fragile than its external documentation suggests: filenames and extensions are derived independently in two or three places that currently happen to agree, an optional config key silently disables the promised symlink if omitted, and the lower-level public entry point produces a different spec filename convention than the higher-level one without disclosing it. None of these are currently live failures — they are latent traps that will fire the next time someone edits one side of a duplicated derivation without noticing the other.

The `mechanics/` scope produced the most severe individual findings in this review, and they are exactly the kind CLAUDE.md pre-flags as bugs rather than acceptable debt: `RigidTendonMusculoskeletalArm` constructs and stores a configured implicit solver (`Kvaerno3`) that its own `__call__` never invokes, silently hand-rolling explicit Euler instead, and `CompliantTendonHillMuscle.extract_outputs` — a method that is part of a real abstract base contract other code calls — returns a hardcoded zero force with a comment admitting it is a placeholder. Both are currently non-symptomatic only because a different code path happens to overwrite or bypass the broken one, which is precisely the fragile "silently substitutes a stale value" pattern the repo's Core Principle section calls out by name. Beyond these two, there is a broader pattern of solver-choice inconsistency (explicit vs. implicit defaults that look swapped relative to their own docstrings; two "equivalent" physics models integrated with different solvers and no documented justification) and of physiological constants (specific tension, vmax) that bypass the `BodyPreset` config abstraction the rest of the codebase uses, in ways adjacent to but distinct from the already-tracked 525249b muscle-geometry-defaults work. On the positive side, Equinox/JAX hygiene in `mechanics/` and `control/` is genuinely clean: no deprecated tree API usage, no Module mutation outside `__init__`, no forbidden `dataclasses.replace` on Modules — the convention violations that were explicitly asked for turned out not to be present, which is worth stating plainly rather than manufacturing findings to fill a quota.

Across all four areas, a recurring meta-pattern is worth naming: comments that admit a problem exist right next to the code that has the problem (`#! Something is wrong here`, `#! TODO: add leaves from self.inputs`, "Return a placeholder", "For simplicity, use Euler step here", "Legacy fallback"). This is a healthier failure mode than silent, undocumented bugs — it means the authors noticed — but it also means these are not undiscovered defects requiring investigation; they are known defects that were deprioritized and then not tracked anywhere durable. Converting these inline admissions into tracked issues (or fixing them outright, several are S-effort) would close the gap between "the author knows" and "the ledger knows," which is exactly the kind of drift the repo's own CLAUDE.md is trying to prevent.
